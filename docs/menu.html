the menu

vm2lxc, design of decision D7 (the interactive front-end). Written 2026-11-17. built and tested against fakes not yet driven by a person on a real host alpha

1. What it is

D7 in docs/BRIEF.md asked for an interactive whiptail menu with a plain-prompt fallback, Enter = the recommended default, progress bars per stage, and a review screen with continue / back / edit / quit. That is this page.

The one idea that keeps it safe: the menu is only a front-end. It asks questions and shows plans, and then it runs this same vm2lxc program with the same flags you could type yourself, and it shows you that exact command line first. It has no code path of its own that touches the host, so it cannot do anything the command line cannot, and every safety rail of the engine (R1 to R29: journal, lock, revalidation, refusal of a RED verdict, teardown on any signal) applies to it unchanged.

2. Ways in

You typeWhat happens
vm2lxc at a terminalopens the menu. With no terminal it is still a usage error (64), as before.
vm2lxc menuthe same; with no terminal it refuses (64) and changes nothing.
vm2lxc menu --no-tuithe same flow with numbered plain prompts, no whiptail. This is also what you get when whiptail is missing, TERM is dumb, or the terminal is smaller than 72x18.
vm2lxc menu --answers FILE [--yes]unattended: no prompts, every answer from the file. See section 6.

3. The screens

Main menu (Enter takes the highlighted default, Esc quits; the default is Scan, the safe first look): Scan, Preflight, Inspect, Convert, Undo, Clean up, Quit.

VM list: the ranked scan as a menu, best candidate highlighted (first green VM by RAM saved). A RED VM can be picked; its own plan refuses it.

The review hub: one screen with the plan, every setting, Continue, Back and Quit. Nothing scrolls and nothing is hidden behind a second page.

 Convert VM 603 "vm2lxc-test-deb12-2disk"
 The exact command Continue runs:  vm2lxc convert 603 --ctid 9100 --hostname vm2lxc-test-deb12-2disk
                                   --memory 1024 --cores 1 --yes
 Nothing runs until you pick Continue. Pick a setting to change it.

   plan        Show the full plan (changes nothing)            <- the highlighted default, first time
   continue    >> Continue: build container 9100 from VM 603, stopping the VM first
   ctid        Container id ........... 9100
   hostname    Hostname ............... vm2lxc-test-deb12-2disk
   memory      RAM (MB) ............... 1024
   cores       Cores .................. 1
   privileged  Privileged container ... no
   start       Start it after creating  no
   back        Back to the VM list
   quit        Quit (nothing is run)

Pick a setting to edit it (an input box, validated; Privileged asks first). The first Enter is the plan. Only after the plan was shown does Continue become the highlighted default, and any edit makes the plan stale again, so the default falls back to plan. Inspect, Undo and Clean up use the same hub with nothing to edit.

Progress: a gauge per run, driven by the engine (section 5), then a result screen with everything the engine printed. If the run failed the result says so and points at vm2lxc cleanup. The result is also left in the terminal's scrollback.

4. Rails

R1 to R29 are in the two earlier design pages and still apply. These are the menu's own. Every row has tests; a mutation check reverts each rail on a copy of the code and the tests that guard it must go red (results in STATUS.md).

#RailWhere
R30The menu is a front-end only: it re-runs the same binary and shows the exact command line before Continue. Itself it only reads: the VM list (the scan), a VM's config, the run journals (to list the conversions undo can act on). Its one non-read, the scratch directory, is R36.menu_cmdline, menu_plan, menu_execute
R31Nothing executes except after an explicit Continue (interactive), or continue=yes in the answers file and --yes on the command line. menu_execute is the only place that adds --yes; menu_plan refuses to carry it. Esc, Cancel, Back, Quit, the end of input and a plan the engine refuses all end in "nothing ran". The first Enter on a review screen is the plan.lib/menu.sh
R32No terminal and no answers file: refuse (64). The menu never hangs waiting for a person who is not there, and never defaults into an action.ui_init
R33The answers file is data, never code: only whitelisted keys, every value validated by the same rules as the command line, a duplicate or unknown key is an error, no control characters, at most 4 KiB, a regular file that is not writable by group or others and is owned by you or root. A key that does not belong to the chosen action is an error (a misspelt ctid must not be ignored). It can never execute on its own. --answers on any command except menu is a usage error.answers_load, menu_answers, vm2lxc
R34Nothing reaches whiptail that it could read as an option: any word starting with - gets a leading space. VM names were already neutralised by the scan (sanitize_text), and text is never interpreted.ui_safe
R35While a run is active, Ctrl-C does not kill the menu: the engine keeps its own handler, which tears the run down, and the menu waits for it and then shows the result. The engine is started with default signal handling so that handler works. A second Ctrl-C (which interrupts the menu's wait) changes nothing: the menu goes on waiting, each run has its own exit-code file, and a teardown the second signal cut short is reported as INCOMPLETE with the way out, vm2lxc cleanup --yes.ui_run
R36The menu's scratch directory is private (0700) and removed when it ends, by two audited helpers in lib/hostexec.sh, the one file that may change anything: scratch_new, and scratch_free, which removes only a directory named vm2lxc-menu.XXXXXX directly under the temp directory, owned by you, not a symlink, holding nothing but plain files (it checks everything before it deletes anything, uses no glob and no recursion, and runs command -p rm so a hostile PATH is not trusted). The progress file is only written if it is an existing plain file (never a symlink: the engine runs as root) and is parsed strictly: a malformed line is dropped, nothing is evaluated.scratch_new, scratch_free, ui_init, ui_cleanup, progress_emit, ui_progress_parse
R37The plain-prompt fallback is the same flow with the same defaults, and a closed input quits instead of looping.ui_menu, ui_input, ui_yesno
R38The convert review screen shows every setting at once and validates each before it is used: container id (free, 100 or higher), hostname (RFC 1123), RAM, cores. Privileged asks first.menu_convert_hub

5. How the progress bar knows

When the menu starts the engine it sets VM2LXC_PROGRESS_FILE. run_apply, run_teardown and the guest-check gate append one tab-separated line just before each step: P stage i n kind. Without the variable nothing is written and the engine behaves exactly as before. Stages and where they sit on the bar:

ActionStages (share of the bar)
convertmount 0-30, checks 30-40, build 40-85, teardown 85-100
inspectmount 0-60, checks 60-80, teardown 80-100
undoundo 0-100
cleanupteardown 0-100 (per run)

Steps are counted by what is actually done, 1 to n, not by their position in the journal. The bar never goes backwards. In the teardown and undo stages a step reads as what is being undone (undoing vm-stop is "Starting the VM again").

6. The answers file

# vm2lxc menu --answers convert.txt --yes
action   = convert
vm       = 603
ctid     = 613
hostname = test-two-disk
memory   = 1024
cores    = 1
privileged = no
start    = no
continue = yes
ActionKeys that apply
scanaction
preflightaction, vm (the exit code is the verdict: 0 / 10 / 20)
inspectaction, vm, continue
convertaction, vm, ctid, hostname, memory, cores, privileged, start, continue
undoaction, ct, continue
cleanupaction, continue

It shows the plan, and executes only with continue=yes in the file and --yes on the command line. --dry-run beats both. A plan the engine refuses (a RED VM, an id in use) stays refused and its exit code is returned.

7. What is not proven

  • No person has driven it on a real terminal yet. The tests use a scripted stand-in for whiptail and stdin for the plain prompts. They prove the flow, the defaults, the arguments whiptail is given and that nothing runs on Esc/Back/Quit, but not how the real whiptail looks or behaves in a given terminal.
  • Ctrl-C is tested (one signal, and a second one in the middle of the teardown), but with the scripted whiptail and a signal sent to the process group. A real terminal and the real whiptail are not in the loop.
  • A second Ctrl-C during the engine's teardown cuts that step short, because timeout --foreground hands the signal to the tool in flight. That is the engine's existing behaviour, not the menu's: the teardown stops as INCOMPLETE and says so, the menu shows it with the way out, and vm2lxc cleanup --yes finishes the job (tested end to end).
  • The terminal-size check (72x18) and the TERM=dumb fallback are read from the real terminal, which the tests do not have.
  • Not part of D7 and not built here: sizing choices (D8), the verified vzdump backup (D9), the soak period (D10), --live (D2).
