Snapshot-mount layer

vm2lxc, snapshot-mount layer. Updated 2026-11-17. Status: LVM-thin verified on a real PVE 9.2 host ZFS only ever run against the fake

1. What it is for

Give the guest-internal checks (and later the copy step) a read-only view of each VM disk's filesystems without ever modifying the source volume, and guarantee that everything it creates is removed again, even on a crash. Decision D1 (storage-level snapshots, not qm snapshot), BRIEF section 6.3.

In this incrementNot yet
LVM-thin: full lifecycle (thin snapshot, read-only loop device, mount, unmount, remove), run for real on a PVE 9.2 host and tested against a stateful fake.
ZFS zvols: full lifecycle (snapshot, read-only clone, mount, unmount, destroy), tested against the same fake only: no real ZFS run yet.
Filesystems: ext2/3/4, XFS, btrfs (default subvolume).
A write-ahead journal, a run lock, vm2lxc inspect <vmid> (plan by default, --yes executes) and a real vm2lxc cleanup. 		qcow2 and Ceph (later, per D1).
Guest LVM / LUKS / mdraid: detected and reported, not opened (needs vgimportclone / unlock).
Running the guest checks' real logic (they still report pending).
Anything that changes the VM or its disks: this layer only ever reads them.

2. Flow

inspect <vmid>                                   (plan is always printed first)
  read: qm config, pvesm path <storage:volume>   -> source dataset / LV for every data disk
  plan: pure function, no host calls
  --yes? no  -> stop here, nothing executed
        yes  -> take run lock, create journal, install trap (EXIT, INT, TERM)
                 1. snapshot   all source zvols in ONE atomic command
                 2. clone      each snapshot, readonly=on, stamped
                 3. dev-ready  settle udev, wait for the device and its partitions
                 4. mount      each supported filesystem read-only under /run/vm2lxc/<run>/
                 5. pick the guest root, run the guest checks against it
        always -> teardown in reverse: umount, destroy clones, destroy snapshot, rmdir, close journal

The source dataset or LV is only ever the origin of a snapshot. It is never opened, written, renamed or property-edited (snapdev=visible would edit it, so it is not used).

5. Journal (write-ahead)

One file per run: /var/lib/vm2lxc/runs/<run>/journal (persistent across reboots, because the clones are). Tab-separated, append-only, human-readable:

# vm2lxc journal v1
RUN   <run>   <vmid>   <epoch>
STEP  <seq>   <kind>   <arg> ...
ST    <seq>   PENDING | DONE | UNDONE | FAILED
CLOSED

A step is journalled PENDING before it runs. A crash therefore leaves a step that may exist, and teardown checks real state before undoing it (so undo is idempotent, and safe to run twice). The latest ST line wins. CLOSED is written only after teardown verified everything is gone.

One flock on /var/lib/vm2lxc/lock serialises inspect --yes and cleanup. cleanup that finds the lock held says so and touches nothing.

6. Safety rails

These matter most, because this is the first code in the project that can destroy anything.

#RailEnforced by
R1Only names matching our patterns are ever destroyed or unmounted (@vm2lxc-<run>, /vm2lxc-<vmid>-<run>-<key>, paths under the run root).host_cmd argument validation
R2Only objects recorded in the journal of a run we own are touched. Nothing is found by scanning or by pattern alone.teardown reads the journal, not the pool
R3Before destroying, re-verify identity: the vm2lxc:run stamp equals the run id, and a clone's origin equals the recorded snapshot. A mismatch refuses, exit 77, and leaves the object alone.undo handlers
R4Never a recursive or forced flag: no -r, -R, -f, no umount -l. A snapshot with dependents therefore fails safe instead of taking children with it.host_cmd allowlist
R5A target equal to a source dataset/LV is refused outright.planner and host_cmd
R6Every mutating command passes one function, host_cmd, an allowlist of exact argument shapes. Anything else dies. It lives only in lib/hostexec.sh.allowlist + static test
R7Mounts are read-only only: the option string must be exactly the read-only set chosen for that filesystem (no remount, bind, loop or extras), only for filesystems in the table above, and only on devices that are ours: our clone or snapshot path, a loop device we attached, or the kernel name (/dev/zdN) of a zvol clone we created.host_cmd mount
R8inspect executes nothing without --yes, and refuses to execute at all in fixture mode and when not root on a PVE node.command code + tests
R9A pre-existing object with the name we are about to create is a refusal, never adopted. The step is journalled FOREIGN, so teardown can never destroy it later, even if its stamp happens to match.apply handlers, teardown
R10Teardown stops at the first failed undo. A mount sits on a loop device or clone, which sits on a snapshot: destroying those while the mount is still there would be wrong. The journal stays open and the next cleanup continues.run_teardown
R11Children never inherit the run lock or the saved stdout/stderr (a long-lived child holding the lock would keep it after we exit). Found on the first real run.host_cmd closes them before exec
R12Every host command is time-bounded (VM2LXC_CMD_TIMEOUT, default 120 s; note that 0 means "no limit", as in coreutils). A hung command cannot wedge a run or its teardown.host_cmd
R13Names never start with - or .: a VG, LV or storage ID like -x would reach an LVM or pvesm command line as an option.name patterns
R15A VM with a lock (backup, rollback, migrate, clone, snapshot-delete, ...) is not snapshotted: something is working on its disks. The plan says so and --yes refuses (exit 77) before creating anything. Backup jobs locked the test VMs on the real host.cmd_inspect
R14SIGINT, SIGTERM and SIGHUP are ignored while tearing down. A signal during teardown must never leave half of what it was removing. SIGKILL still works, and cleanup recovers from the journal.inspect_trap
R16The journal is honest. A step that cannot be recorded is not performed (a failed write or an unopenable journal stops the run before the action). A teardown that cannot update the journal reports failure and leaves the run open instead of closing it. Journal arguments that are empty or contain a tab or newline are refused, because they would shift fields on reading. The directories are fsynced.journal_step, journal_mark, journal_close
R17"Could not tell" is never "absent". An undo probe treats only the exact answer as gone (mountpoint says not a mountpoint, zfs says "does not exist", the LV is missing). A timeout, a refusal, an I/O error or an unreadable path is an error: the step is not marked undone and teardown stops (R10).undo handlers, zfs_exists
R18Nothing the guest or a file controls reaches an interpreter or the host. Journal fields are validated before they are used as array subscripts (a crafted sequence number would otherwise execute code). A guest path is resolved on the host and must stay inside the guest root (an absolute symlink /etc -> /etc points at the host). Terminal text is stripped of ASCII controls, UTF-8 C1 controls and bidi overrides in any locale.journal_load, path_inside_root, sanitize_text
R19Trust anchors are fixed. Outside the test seam every tool must resolve to a system directory (a hostile PATH cannot substitute its own zfs or mount), and the run root is always /run/vm2lxc (an environment variable cannot point our mounts elsewhere). The ownership stamp is read with -s local: a value inherited from a parent dataset is not proof. Device names containing .. or spaces are never ours.host_cmd, run_root, hc_mount
R20The VM is read again after the run lock is taken. A backup can start, or a disk move, between the plan being shown and the lock being acquired. The config, the lock and the plan are rebuilt and compared; any difference refuses the run (exit 77) with nothing created.inspect_revalidate
R21Only our own devices are mounted. lsblk also lists children: a guest LVM volume group or md array that udev activated on one of our partitions shows up as a device. Only loop, part and disk rows are mounted; the others are skipped and reported, and the run goes on.act_do_mount_disk

8. Verified on a real host (PVE 9.2.28, LVM-thin)

Everything here was done on a live hypervisor against four disposable test VMs (Debian 12, Ubuntu 24.04, Alpine, and a two-disk Debian), checked against a baseline taken before each run.

  • Lifecycle: thin snapshot, read-only, activated, read-only loop device, filesystems mounted ro,noload, guest root found, teardown. Host back to the baseline every time: same LV list, same thin-pool usage, no loop devices, no mounts, journal CLOSED, nobody holding the lock. The VMs kept running.
  • Layouts seen: a root plus an EFI partition, two ext4 partitions (root plus boot), and a whole-disk ext4 with no partition table.
  • Source never modified: on a stopped two-disk VM, the sha256 of both source volumes was identical before and after a run (the BRIEF's checksum proof).
  • Crash injection: 61 runs killed at points through the execution window with SIGKILL, SIGTERM and SIGHUP. SIGKILL leaves at most a stray snapshot LV and cleanup --yes restored the exact baseline each time. The sweep also found two real gaps (a signal during teardown aborted it; SIGHUP had no handler), both fixed and re-verified: 26 of 26 later TERM/HUP runs left the host clean.
  • Re-verified after the independent review's fixes: the deployed source was identical to HEAD; inspect --yes on all four VMs left the host at its baseline fingerprint; the live /proc/mounts showed ro,nosuid,nodev,noexec,relatime,norecovery (the kernel's spelling of our noload); SIGTERM, SIGHUP and a reader going away (SIGPIPE) tore down clean, and after a SIGKILL cleanup --yes restored the baseline exactly.
  • Found only by the real run: LVM reported the leaked lock descriptor (R11); PVE 9 prints a Total (KiB) storage header, template: null in the VM list, and a 30-minute month RRD step.

9. Still unverified

  • ZFS has never run on real hardware. pvesm path printing /dev/zvol/<pool/ds> for a zfspool volume is an assumption (the lvmthin form, /dev/<vg>/<lv>, was confirmed).
  • zfs snapshot -o vm2lxc:run=... and zfs clone -o readonly=on -o vm2lxc:run=... are accepted for zvols on PVE 8/9's OpenZFS.
  • zvol partition nodes appear as <clone>-part1 after udevadm settle.
  • XFS and btrfs guests have not been mounted for real (ext4 has).
  • PVE 8.x has not been run (only 9.2.28).
  • A guest with LUKS, LVM or mdraid inside is reported as skipped, but was only tested against the fake.
  • Kernel names for zvols. The real lsblk -p prints /dev/zdN and /dev/zdNpM, not /dev/zvol/.... The code now resolves the clone with readlink -f and accepts only the zd device it created, but this path has only run against the fake (the independent review found that the first version would have refused every ZFS mount).

10. Open questions

  1. Is vm2lxc inspect <vmid> (plan by default, --yes to execute) the right user-facing name? It has proven useful on its own.
  2. Clones are created next to the source zvol, so Proxmox lists them as orphan volumes while a run is live. Acceptable, or use a dedicated scratch dataset (one persistent object to create and own)?
  3. Where should the journals live long term: /var/lib/vm2lxc/runs/ as built, or per-VM as BRIEF 4.10 sketched?
