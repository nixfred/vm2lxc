convert and undo

vm2lxc, design of the conversion. Updated 2026-11-17. Status: verified on a real PVE 9.2 host with four guest types LVM-thin only; ZFS is tested against a fake alpha

1. What it does

vm2lxc convert <vmid> turns a QEMU VM into a new LXC container. The VM is never deleted and its disks are never written: the only things ever done to it are a graceful shutdown and onboot 0 (and, by undo, start and onboot 1). vm2lxc undo <ct> reverses it. Without --yes both commands only print the plan.

2. The pipeline

 plan (read-only)   verdict, container id/hostname/sizes, the VM's MAC and bridge, the steps
 --yes
 PHASE A   (the same engine as `inspect`: write-ahead journal, run lock, signal traps)
   vm-stop      graceful shutdown: stop-and-copy (D2), so the snapshot is consistent
   vm-onboot    autostart off (D3): a VM that boots beside its container is the worst outcome
   snapshot     storage-level snapshot of every source volume (thin LV or ZFS)
   mount        read-only: loop device, ext4 `ro,noload,nodev,nosuid,noexec`
 GATE      find the guest root, run the 12 guest checks.  RED  => tear down, restart the VM, exit 77
 PHASE B   (decided from what the guest says)
   stage-dir    /var/tmp/vm2lxc/<run>/
   tar-create   the boot filesystem (and each extra disk) archived with --numeric-owner --xattrs --acls
   ct-create    pct create from the archive: unprivileged (D5), the VM's exact MAC (D4), tags vm2lxc;vm2lxc-<run>,
                created stopped, never starting at boot, ostype unmanaged
   ct-mount     pct mount
   ct-fixup     in the container's COPY: fstab lines naming the VM's disks commented (backup kept), cloud-init
                disabled, netplan MAC-match removed, serial getty and kernel mounts masked
   ct-copy-disk each extra disk into its mount point (D6), at the path the guest's fstab gives it
   ct-unmount
   ct-start     only with --start (the cutover)
 COMMIT    ct-create, vm-stop, vm-onboot, ct-start become KEPT; the journal says COMMITTED
 TEARDOWN  everything else (snapshot layer, staged archives) is undone, newest first

3. Decisions applied (from the BRIEF)

#DecisionHow it is done
D1storage-level snapshots, not qm snapshotthe snapshot layer; nothing is added to the VM's config
D2stop-and-copy is the defaultvm-stop before the snapshot; --live is not built
D3autostart off; never two live copiesvm-onboot; undo refuses to start the VM while the container runs
D4VM's exact MAC, no guest network rewritehwaddr copied; the interface name is read from the guest's own network config; ostype unmanaged
D5unprivileged by default; Docker refused--privileged is opt-in; the Docker guest check is RED

D9identity files keptmachine-id, SSH host keys, hostname are copied

Not built yet: --live two-pass copy (D2), whiptail UI (D7), sizing choice UI (D8), vzdump backup and test restore (D9), soak period (D10), post-conversion compare (D12).

4. Safety rails added for convert and undo

These extend R1-R21 in snapshot-layer.html. All of them live behind the same host_cmd allowlist.

#RailEnforced by
R22Stop-and-copy, gracefully. The VM is shut down, never force-stopped; if it will not stop, nothing is created and nothing is snapshotted.act_do_vm_stop
R23The VM is never deleted and its disks never written. The qm validator allows only status, start, shutdown --timeout N and set --onboot 0|1, and only on this run's VM.hc_qm
R24One container, identified by a tag. It is created stopped, never starting at boot, tagged vm2lxc-<run>. A container that already has the wanted id is never adopted and never destroyed (journal state FOREIGN). Only this run's container id is accepted by pct.act_do_ct_create, hc_pct
R25A closed option set for pct create. Every option from a fixed list, every value against its own pattern; the archive must be this run's staged rootfs.tar. No password, no SSH keys, no raw lxc.* keys, no privileged flags.hc_pct_create
R26Fix-ups never run guest code and never follow a guest symlink. Every path is resolved chroot-style first (an absolute symlink is re-rooted under the container), then edited by host tools (sed, cp, touch, ln) with pinned expressions, inside the unprivileged user namespace. A guest symlink to a host file is neither edited nor copied in (tested for fstab, netplan, cloud-init and the unit masks).act_do_ct_fixup, hc_ctedit, hc_usernsexec
R27Extra-disk data goes only into a verified mount point. The destination is resolved chroot-style and must pass mountpoint -q; otherwise the write would silently fill the root filesystem. The volume's own lost+found is never replaced.act_do_ct_copy_disk, hc_tar
R28undo is as careful as convert. It stops and destroys the container only if it carries this run's tag; it starts the VM only if it was running before, and never while the container runs. A committed conversion is not mistaken for a crash by cleanup.act_undo_ct_create, act_undo_vm_stop, journal KEPT/COMMITTED
R29No silent data loss. A second data filesystem on the boot disk that the guest does not mount at /boot or /boot/efi refuses the conversion (nothing changed, VM restarted). An extra disk with more than one mountable filesystem is refused too.conv_decide
R39USB devices are mapped only when they are certain. Each usbN setting is looked up on the host after the VM has stopped (QEMU has let go of the device). Exactly one match by vendor:product, or the named port, gives a devN entry for the raw USB node and for its ttyUSB/ttyACM port if the host driver made one. No match, two identical devices, a cluster mapping= or an unknown setting maps nothing, never a guess, and is said three times: in the plan, in the notes and in the final summary. pct create accepts --devN only for /dev/bus/usb/BBB/DDD and /dev/ttyUSBn|ttyACMn, with no options. Proxmox gives the node to the container's root, mode 0660 (read from PVE 9.2's own code).usb_resolve, conv_decide, RE_CT_DEV in hc_pct_create

5. Failure matrix (each is a test; the fake injects the failure)

FailureResult
the VM will not shut downnothing is snapshotted or created; the VM is untouched
a guest check is RED (Docker, NFS server, DKMS, disk layers, ...)exit 77, snapshot layer torn down, the VM restarted
pct create failsteardown, VM restarted, no container, journal closed
pct mount or a fix-up fails after the container existsthe half-built container is destroyed (it carries the run's tag), the VM restarted
an extra volume is not mounted where expectedrefused before writing a byte; rollback
the container id was taken meanwhilerefused ("it will not be adopted"); the other container is left alone
a second data filesystem on the boot diskrefused with the reason; rollback
SIGTERM / SIGHUP / SIGPIPE during the copyteardown, VM restarted (exit 143 / 129 / 141)
SIGKILL after the container existsthe journal is open; cleanup --yes destroys the container and restarts the VM
the tag of the container was changed before undoleft alone (R28); nothing started
the VM was already stopped before the conversionnothing is stopped; undo leaves it stopped and says so

6. Verified on a real host

Proxmox VE 9.2.28, LVM-thin, four disposable test VMs (tag vm2lxc-test-rm), each converted into a container and undone again. After every run the host was compared with a baseline: no snapshot LV, no loop device, no mount, no staging directory, no open journal.

7. Not verified, or not done

  • ZFS has never run on real hardware (including the kernel-name /dev/zdN handling). Only the fake has run it.
  • Proxmox VE 8.x has not been run; neither has a privileged container (--privileged) or qcow2/Ceph/dir storage.
  • DHCP guests keep their MAC, not necessarily their IP. The container of VM 600 got a different lease from the VM. The address is the DHCP server's decision; a reservation by MAC pins it. A guest with a static address keeps it.
  • Tailscale: the state is copied, the VM is set not to autostart, and the output warns loudly, but undo does not copy state back into the VM.
  • The container keeps the guest's kernel and initramfs packages (unused). Staging needs free space in /var/tmp about the size of the guest.
  • One filesystem per extra disk; guest LVM, LUKS and RAID are refused (RED).
  • USB mapping (R39) has only run against the fake host (and its sysfs reader against hex's real sysfs, read-only). No real USB device has been mapped into a real container yet. The bus/device number in /dev/bus/usb/BBB/DDD changes when the device is replugged, so the entry then needs a fresh pct set. Inside the container a serial port keeps the host's name (ttyUSB1, not necessarily the ttyUSB0 the guest used). PCI passthrough stays RED.
